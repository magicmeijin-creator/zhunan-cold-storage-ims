## 操作流程

1. 安裝 Node.js
2. 下載此專案，並在VS Code上開啟資料夾
3. 打開productstock_mysql、multi_unit_migration.sql檔案並執行過一遍
4. 確認路徑正確，在PowerShell(終端機)輸入：
   - cd　(路徑檔案)
   - npm install
   - npm start
5. 執行

## 新增揀貨流程：
 - 進貨 --> 放入倉儲地圖 --> 
 - 出貨流程 -> 選取出貨資料 -> 勾選我已確認 -> 勾選彈出視窗 -> 出貨 -> 出貨單出現揀貨單(待揀貨) -> 確認揀貨 -> 揀貨紀錄產生 -->
 - 完成生鮮庫存清單、倉儲地圖區塊 更新 --> 流程完成
## 盤點功能- 整體流程：
 - 選擇倉庫與區域 → 建立盤點單 → 逐格確認商品批次與實際數量（空格也需記錄）→ 完成所有格位盤點 → 查看帳面與實際數量差異 → 確認更新倉儲狀況 → 系統同步調整庫存與倉- 儲地圖 → 留下盤點異動紀錄 → 流程完成
## 倉儲地圖功能- 整體流程：
  建立倉庫 → 新增倉儲區域與格位 → 進貨後選擇商品批次與空格位 → 將商品上架至指定位置 → 查看各區域與格位的庫存狀況 → 需要時移動商品至其他空格位 → 系統更新倉儲地圖並留下異動紀錄 → 流程完成
## 紀錄查詢功能- 整體流程：
  開啟「紀錄查詢」→ 選擇日期範圍、紀錄類型或輸入關鍵字 → 查看符合條件的進貨、出貨、報廢、盤點與倉位異動紀錄 → 點選紀錄追溯商品批次、數量、時間與相關位置 → 查詢完成

## 四項要求

1. 跟大黑版比起來效率
   人工大黑版沒有先進先出功能
   不能直接看到逾期貨物
   而且當貨物一多的時候
   一個大黑版會應付不來
   再加上現在蔬果種類繁多 分類上很麻煩
   如果改用系統方式的管理
   除了解決以上問題以外
   資訊也會更好管理以及統整

2. 出貨防呆機制
   出貨時，系統會顯示各批次的商品、效期與可用庫存，並檢查輸入數量是否大於該批次的現有數量。若數量不合理或庫存不足，系統會阻止出貨並提示使用者修正，避免庫存被扣成負數或出錯批次。出貨完成後，系統會更新庫存、記錄異動時間與數量，並同步處理該批次在倉儲格位中的存放數量，降低人工登記遺漏的情況。

3. 盤點改善功能
   系統提供依倉庫區域進行的盤點功能，使用者可逐格記錄現場商品批次與實際數量，並透過進度顯示掌握盤點狀況。所有格位完成盤點後，系統會呈現帳面數量與實際數量的差異，讓使用者確認後再更新庫存與倉儲地圖。盤點造成的庫存調整會留下異動紀錄，方便日後追溯；盤點進行期間也會限制該區域的部分庫存操作，降低盤點資料受到即時異動影響的機會。

4. 先進先出功能
   系統以批次管理每次進貨，保存進貨日期與到期日，並在庫存列表中依效期優先、進貨日期次序呈現批次，協助使用者優先處理較早到期或較早入庫的商品。出貨前可查看批次資訊與效期提醒，減少舊批次長期滯留及商品逾期的風險。蔬果保存期限差異較大，因此系統會優先提醒效期較近的批次，再以進貨時間作為排序參考。


## 詳細細節註解(舊版) ##

# Productstock 前端與 MySQL API

這個版本用原本的 HTML 畫面搭配 Express API 連線 MySQL。瀏覽器只呼叫同源 API，資料庫帳密放在伺服器端的 `.env`。

## 使用方式

1. 新資料庫可使用 MySQL 8.0 匯入 `productstock_mysql.sql`。既有資料庫請先備份，再依序執行尚未套用的更新檔（至少包含 `warehouse_migration.sql`、`outbound_orders_migration.sql`；多單位與盤點功能則另需執行對應 migration）。不要對既有資料庫重新匯入含 `DROP DATABASE` 的完整 schema。
2. 安裝 Node.js 18 或更新版本。
3. 在此資料夾複製 `.env.example` 為 `.env`，填入 MySQL 使用者與密碼。
4. 在此資料夾執行 `npm install`，再執行 `npm start`。
5. 開啟 `http://localhost:3000`。可在 `http://localhost:3000/api/health` 查看 API 是否能連上資料庫。

MySQL 使用者需要 `productstock` 資料庫的讀寫權限。不要把 `.env` 或資料庫密碼放進前端 HTML/JavaScript，也不要把 `.env` 提交到版本控制。

## 目前串接功能

- 庫存清單從商品、供應商和庫存批次表讀取；每列代表一個庫存批次。
- 新增進貨會在同一個資料庫交易中建立（必要時）商品和供應商、進貨單、進貨明細、批次與 `PURCHASE` 異動。
- 報廢會鎖定批次、檢查可用庫存、更新批次數量與狀態，並寫入 `WASTE` 異動；一般出貨透過下方的出貨單流程處理。
- 倉儲地圖可建立倉庫區域和格位、查看空位／已存放批次、將未上架庫存放入空格、在格位間移庫，並保留格位異動紀錄。
- 商品進銷存總覽與倉儲地圖可透過兩個介面共用的左側導覽互相切換；手機版可展開／收起導覽。
- 從總覽執行報廢時，系統會同步從已上架格位扣除數量並留下下架紀錄。
- 一般出貨會先建立「待揀貨」出貨單，預留批次與實際格位庫存；員工依單取貨後，在左側「出貨單」頁確認揀貨完成，系統才一次更新批次庫存、倉儲格位及出貨紀錄。取消待揀貨單會釋放預留量。
- 搜尋、類別／效期篩選、排序和提示數字由資料庫資料計算。

## Schema 限制

目前提供的 schema 沒有產地、溫層、使用者登入或權限欄位，所以介面只顯示供應商，溫層顯示「未設定」，也尚未包含登入功能。商品代碼和批次號由 API 自動產生。成本預設為 0，進貨表單可以輸入單位成本。每格最多存放一個批次；同一批次可分配到不同格位。

這是本機開發用的基本 API 範例；若部署到可被外部存取的伺服器，還需要加入登入授權、HTTPS、請求限制及正式的資料庫權限管理。
